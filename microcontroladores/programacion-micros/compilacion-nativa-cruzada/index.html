LA COMPILACIÓN NATIVA Y LA COMPILACIÓN CRUZADA

INTRODUCCIÓN

Los equipos linux utilizan como compilador nativo GCC. Cuando comenzamos a programar microcontroladores es habitual instalar herramientas como AVR-GCC cuando queremos trabajar con un ATmega o un ATtiny, ARM GCC para programar un STM32 o ESP-IDF para un microcontrolador de Espressif, sin preguntarnos por qué no basta con utilizar el compilador gcc que ya viene instalado en Linux. La respuesta está en dos conceptos fundamentales del desarrollo de software: la compilación nativa y la compilación cruzada (cross compilation).

Comprender esta diferencia es esencial para desarrollar firmware para microcontroladores como los ATmega, ATtiny, STM32 o ESP32, especialmente si utilizamos una computadora como una Raspberry Pi 5 como estación de desarrollo

LA COMPILACIÓN NATIVA

Se denomina compilación nativa al proceso mediante el cual un compilador genera un programa destinado a ejecutarse sobre la misma arquitectura donde dicho compilador está funcionando

Supongamos que estamos trabajando en un equipo que corre bajo linux, específicamente una Raspberry Pi 5. La Raspberry Pi posee un procesador ARM64 y el compilador gcc instalado por el sistema operativo también se ejecuta sobre esa arquitectura

Cuando ejecutamos en la terminal:

gcc programa.c -o programa

El resultado será un ejecutable para ARM64 que correrá desde la terminal de la R-Pi5.

En este caso, el equipo donde se compila y el equipo donde se ejecutará el programa son, desde el punto de vista de la arquitectura, el mismo. La mayoría de las aplicaciones de escritorio y muchas utilidades de Linux se desarrollan mediante compilación nativa.

LA COMPILACIÓN CRUZADA

La compilación cruzada ocurre cuando el compilador se ejecuta sobre una arquitectura determinada, pero genera código máquina destinado a otra arquitectura diferente.

Por ejemplo, si utilizamos una Raspberry Pi 5 para desarrollar firmware para un ATmega328P, el compilador que utilizaremos no debe generar instrucciones ARM64, sino instrucciones para un AVR.

En ese caso utilizaremos:

avr-gcc programa.c -mmcu=atmega328p

Aunque el compilador se está ejecutando sobre un procesador ARM64, el código generado está pensado exclusivamente para un microcontrolador AVR. Precisamente por eso recibe el nombre de compilador cruzado (cross compiler).

INCOMPATIBILIDAD DEL COMPILADOR GCC ESTÁNDAR EN MICROCONTROLADORES

Muchos piensan que el compilador gcc sirve para compilar cualquier código en C. Esto es un error. Aunque el lenguaje C se escribe igual en todos lados, el chip de una computadora (ya sea Intel, AMD o un ARM de una Mac/Laptop moderna) tiene recursos gigantescos. En cambio, el chip de un microcontrolador es diminuto y habla un dialecto totalmente diferente. Una computadora (con chip Intel, AMD o ARM) procesa la información con un sistema operativo completo. Un microcontrolador corre el código directamente en el hardware, es decir en él mismo.

Por eso, el gcc estándar de tu computadora solo crea programas para sistemas operativos de computadora no sirve para la arquitectura limitada de un microcontrolador. Para ello necesitas un compilador especial que traduzca el código a su escala.

Consideremos el siguiente programa:

#include <avr/io.h>
int main(void) 
{
    DDRB |= (1 << PB5);
    
    while (1) 
    {
        PORTB ^= (1 << PB5);
    }
}

Este programa manipula directamente los registros del ATmega328P. Si intentamos compilarlo con gcc programa.c, obtendremos errores porque:

  • gcc no conoce la biblioteca avr/io.h.
  • Desconoce los registros propios de la arquitectura AVR.
  • Genera instrucciones ARM, no instrucciones AVR

En cambio, utilizando

avr-gcc programa.c -mmcu=atmega328p

el compilador reconoce la arquitectura AVR, las bibliotecas correspondientes y genera un ejecutable adecuado para el microcontrolador.

FUNCIONAMIENTO DE UN COMPILADOR CRUZADO

Un compilador cruzado no solo genera el código máquina para una arquitectura distinta de aquella en la que se ejecuta. También incluye el conjunto de herramientas y recursos necesarios para desarrollar aplicaciones destinadas al microcontrolador objetivo, entre ellos:

  • Bibliotecas estándar adaptadas al microcontrolador de destino.
  • Archivos de cabecera con la definición necesaria para trabajar con el hardware del dispositivo.
  • El ensamblador y el enlazador (linker).
  • Scripts de enlazado que describen la distribución de la memoria.
  • Herramientas para generar archivos ejecutables y de programación en formatos como ELF, BIN o HEX.
  • Utilidades para el análisis, depuración y manipulación de archivos binarios.

Por ejemplo, la cadena de herramientas para AVR suele incluir: avr-gcc, avr-libc, avr-ld, avr-objcopy, avr-size y avr-ar. Todas estas herramientas trabajan conjuntamente para producir el firmware que finalmente será grabado en el microcontrolador.

Flujo de trabajo del código fuente al microcontrolador

En un proyecto típico para un microcontrolador STM32, por ejemplo una placa NUCLEO-F446RE, el flujo de trabajo comienza con el código fuente escrito por el desarrollador y termina con la programación del firmware en la memoria Flash del dispositivo. Utilizando la GNU Arm Embedded Toolchain, el proceso desde la terminal puede representarse de la siguiente manera: 


            # 1. Compilar el código fuente
            arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb \
                -c main.c -o main.o

            # 2. Enlazar el programa
            arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb \
                main.o startup_stm32f446xx.o \
                -T STM32F446RE_FLASH.ld \
                -o firmware.elf

            # 3. Generar el archivo para programar el microcontrolador
            arm-none-eabi-objcopy -O binary firmware.elf firmware.bin

            # (Opcional) Generar un archivo Intel HEX
            arm-none-eabi-objcopy -O ihex firmware.elf firmware.hex

            # 4. Programar el microcontrolador mediante ST-Link
            st-flash write firmware.bin 0x08000000

En un proyecto típico para AVR, el flujo de trabajo es el siguiente:

  1. Código fuente (.c)[cite: 1]
  2. Compilación con avr-gcc[cite: 1]
  3. Generación de archivo ELF (.elf)[cite: 1]
  4. Procesamiento con avr-objcopy[cite: 1]
  5. Generación de archivo HEX (.hex)[cite: 1]
  6. Transferencia con avrdude[cite: 1]
  7. Ejecución en el microcontrolador AVR[cite: 1]

El archivo .elf contiene el programa junto con información de depuración[cite: 1]. Posteriormente, avr-objcopy genera el archivo hex, que contiene únicamente los datos necesarios para programar la memoria Flash del microcontrolador[cite: 1]. Finalmente, herramientas como AVRDUDE transfieren ese archivo al dispositivo mediante un programador, como un USBasp o un Arduino configurado como ISP[cite: 1].

Conceptos de Host y Target

En compilación cruzada aparecen dos términos muy utilizados[cite: 1]:

  • Host: Es el equipo donde se ejecutan las herramientas de desarrollo[cite: 1].
  • Target: Es el dispositivo para el cual se genera el programa[cite: 1].

Ejemplo 1:

  • Host: Raspberry Pi 5[cite: 1]
  • Compilador: AVR-GCC[cite: 1]
  • Target: ATmega328P[cite: 1]

Ejemplo 2:

  • Host: PC con Windows[cite: 1]
  • Compilador: arm-none-eabi-gcc[cite: 1]
  • Target: STM32F446RE[cite: 1]

En ambos casos existe compilación cruzada porque el programa no se ejecutará en el mismo sistema donde fue compilado[cite: 1].

Compiladores cruzados habituales

Dependiendo de la arquitectura del microcontrolador se utilizan distintas cadenas de herramientas[cite: 1]:

Compilador Arquitectura destino
avr-gcc AVR (ATmega, ATtiny)
arm-none-eabi-gcc ARM Cortex-M
riscv-none-elf-gcc Microcontroladores RISC-V
xtensa-esp32-elf-gcc ESP32 basados en Xtensa

Todos ellos derivan del proyecto GNU Compiler Collection (GCC), pero cada uno está configurado para generar código máquina para una arquitectura diferente y acompañado por las bibliotecas y herramientas específicas de su plataforma[cite: 1].

Importancia de la compilación cruzada en sistemas embebidos

Los microcontroladores suelen disponer de recursos muy limitados: poca memoria RAM, escasa memoria Flash y una capacidad de procesamiento reducida[cite: 1]. Muchos ni siquiera ejecutan un sistema operativo[cite: 1].

Por ello, el desarrollo normalmente se realiza en un equipo mucho más potente —como una computadora de escritorio o una Raspberry Pi—, donde se editan los archivos, se compilan, se depuran los errores y finalmente se genera el firmware[cite: 1]. Ese firmware se transfiere posteriormente al microcontrolador mediante un programador o un depurador[cite: 1].

Este método permite desarrollar de forma cómoda y rápida sin depender de las limitaciones del dispositivo destino[cite: 1].

Conclusión

La diferencia entre compilación nativa y compilación cruzada radica en el destino del código generado[cite: 1].

En la compilación nativa, el compilador produce un programa para la misma arquitectura donde se está ejecutando[cite: 1]. Es el caso del comando gcc utilizado para crear aplicaciones que funcionarán directamente en una Raspberry Pi o en un PC[cite: 1].

En la compilación cruzada, en cambio, el compilador se ejecuta en un equipo anfitrión (host), pero genera código para una arquitectura distinta, denominada target[cite: 1]. Este es el modelo habitual en el desarrollo de firmware para microcontroladores, donde herramientas como AVR-GCC o arm-none-eabi-gcc permiten crear programas para dispositivos que no podrían compilar su propio código[cite: 1].

Comprender esta diferencia facilita entender por qué existen distintas cadenas de herramientas para cada familia de microcontroladores y por qué instalar únicamente gcc no es suficiente cuando se trabaja con sistemas embebidos[cite: 1].
