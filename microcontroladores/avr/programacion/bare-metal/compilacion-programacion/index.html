COMPILACIÓN Y GRABACIÓN DE FIRMWARE PARA MICROCONTROLADORES AVR DESDE LA LÍNEA DE COMANDOS

INTRODUCCIÓN

La programación de microcontroladores AVR no requiere obligatoriamente un entorno de desarrollo integrado (IDE) como Arduino IDE, Microchip Studio, MPLAB X IDE o IAR Embedded Workbench para AVR. En equipos escasos de recursos o entornos de desarrollo limitados, estas herramientas se hacen inviables.

Toda la cadena de herramientas puede utilizarse directamente desde la línea de comandos, lo que permite comprender mejor el proceso de generación del firmware, automatizar tareas mediante scripts o Makefiles y trabajar en cualquier sistema GNU/Linux.

En este artículo se muestra el proceso completo para compilar un programa escrito en lenguaje C, generar el archivo ejecutable para el microcontrolador y grabarlo en la memoria Flash utilizando un programador USBasp.

1. ESCRIBIR EL PROGRAMA

El primer paso consiste en escribir el programa que ejecutará el microcontrolador. En este artículo utilizaremos el lenguaje C, ya que es el lenguaje más utilizado para desarrollar aplicaciones sobre microcontroladores AVR. Aunque existen otros lenguajes y herramientas que permiten programarlos, prácticamente toda la documentación, ejemplos y bibliotecas oficiales están pensadas para C.

El programa lo guardaremos en un archivo de código fuente cuya extensión es .c. Este archivo no contiene instrucciones que el microcontrolador pueda ejecutar directamente; únicamente almacena el código escrito por el programador en un formato de texto plano. Dicho de otra manera, es un archivo legible por una persona, pero todavía incomprensible para el microcontrolador. Más adelante será el compilador quien se encargue de traducirlo al lenguaje máquina.

Para escribir el programa puedes utilizar cualquier editor de texto. En GNU/Linux existen muchas alternativas, como nano, vim, emacs, Visual Studio Code, Geany o incluso un editor gráfico sencillo como Gedit. En este artículo utilizaremos nano, ya que está instalado por defecto en la mayoría de distribuciones y resulta muy fácil de usar desde la línea de comandos.

Antes de crear el archivo conviene abrir una terminal y situarse en la carpeta donde deseamos guardar el proyecto. Puedes crear una carpeta específica para tus programas AVR o utilizar cualquier directorio de trabajo. Por ejemplo: 

mkdir avr
cd avr

Todos los archivos que vayamos creando durante el desarrollo (código fuente, archivos objeto, ejecutables y archivos para programar el microcontrolador) se generarán dentro de esta carpeta que hemos denominado avr (puede ser cualquier otro nombre). Esto permite mantener todos los archivos relacionados con el proyecto en un solo lugar, lo que facilita mantener organizado el proyecto.

Una vez dentro del directorio de trabajo, creamos un nuevo archivo llamado blink.c ejecutando: 

nano blink.c

Al hacerlo, nano abrirá un archivo nuevo. Si el archivo ya existía, simplemente lo abrirá para editarlo.

Escribimos entonces el siguiente programa: 


    #include <avr/io.h>
    #include <util/delay.h>

    int main(void)
    {
        DDRB |= (1 << DDB1);      // PB1 como salida

        while (1)
        {
            PORTB ^= (1 << PORTB1);
            _delay_ms(300);
        }
    }

Una vez terminado, debemos guardar el archivo. En nano se hace presionando Ctrl + O (de Write Out). El editor mostrará el nombre del archivo, en este caso blink.c. Simplemente presionamos Enter para confirmar. Después salimos del editor con Ctrl + X.

El nombre del archivo puede ser cualquiera siempre que termine con la extensión .c. Por ejemplo, led.c, contador.c, prueba.c o main.c. En este artículo utilizaremos el nombre blink.c porque el programa hace parpadear un LED.

En este punto únicamente hemos creado el código fuente. Es decir, un archivo de texto que contiene instrucciones escritas en lenguaje C. Todavía no existe un programa que el microcontrolador pueda ejecutar. En el siguiente paso utilizaremos el compilador avr-gcc, que traducirá este código fuente a lenguaje máquina para el ATmega328P.

2. COMPILAR EL PROGRAMA

En este ejemplo trabajaremos con un ATmega328P, el mismo microcontrolador que incorpora la placa Arduino Uno. Si utilizas otro AVR, no hay ningún problema: el procedimiento será exactamente el mismo. Lo único que cambiará será el modelo de microcontrolador que indicaremos al compilador y al programa de grabación. 

avr-gcc -mmcu=atmega328p -DF_CPU=16000000UL -Os blink.c -o blink.elf

Este es el comando que transforma el archivo blink.c en un programa ejecutable para un microcontrolador AVR. Aunque solemos decir que avr-gcc compila el programa, en realidad hace bastante más.

Primero ejecuta el preprocesador, que procesa las directivas como #include y #define. Después traduce el código C a lenguaje ensamblador. A continuación, el ensamblador convierte ese código en instrucciones máquina para la arquitectura AVR. Finalmente, el enlazador (linker) une el programa con las bibliotecas necesarias y genera un archivo ejecutable en formato ELF.

Veamos con más detalle qué hace cada uno de los parámetros utilizados.

Parámetro -mmcu=atmega328p

Este parámetro indica el modelo exacto del microcontrolador para el cual se está compilando el programa. En este caso, se trata de un ATmega328P.

Esta información es fundamental para el compilador. Gracias a ella sabe qué conjunto de instrucciones puede utilizar, cómo está organizada la memoria del dispositivo, qué registros de hardware existen,cuáles son las direcciones de esos registros y qué archivos de soporte debe enlazar durante la compilación.

Si se especifica un microcontrolador incorrecto, el programa podría compilar sin mostrar errores, pero el código generado podría utilizar registros o instrucciones que el microcontrolador real no posee, provocando un funcionamiento incorrecto o incluso impidiendo la programación del dispositivo.

Si no conoces el modelo exacto de tu microcontrolador, puedes encontrarlo impreso sobre el encapsulado. Por ejemplo:

  • ATmega328P-PU
  • ATmega88PA-PU
  • ATtiny85
  • ATmega16A

Ese nombre comercial también determina el identificador que utilizaremos con avr-gcc.

Si usamos otro microcontrolador como el ATmega88PA, el parámetro sería -mmcu=atmega88pa. Es importante escribirlo exactamente como corresponde al modelo del microcontrolador, ya que el compilador distingue entre mayúsculas y minúsculas y requiere la forma correcta para generar el código adecuado.

Para saber el identificador del microcontrolador que usamos, podemos listar todos los micros soportados por avrdude escribiendo en una terminal:

avrdude -p ?

Y nos dará un extenso listado con los códigos de los micros soportados por el grabador

...

...

Parámetro -DF_CPU=16000000UL

Este parámetro define la constante F_CPU, que representa la frecuencia de funcionamiento del microcontrolador expresada en hercios (Hz) . En este caso son 16 millones de HZ.

En este ejemplo, 16000000 significa que el microcontrolador funciona a 16 000 000 ciclos por segundo, es decir, 16 MHz.

Es importante comprender que F_CPU no configura la frecuencia del microcontrolador. No modifica fusibles (fuses), no cambia el oscilador interno ni altera el cristal de cuarzo. Simplemente informa al compilador cuál será la frecuencia de reloj para que pueda generar determinados cálculos correctamente.

Muchas bibliotecas de AVR utilizan esta constante. Un ejemplo muy conocido es <util/delay.h>, donde funciones como _delay_ms() y _delay_us() calculan el número de ciclos de reloj necesarios para producir el retardo solicitado.

Si no se define F_CPU y el programa utiliza estas funciones de retardo, normalmente el compilador emitirá advertencias o errores, ya que no dispone de la información necesaria para calcular los tiempos correctamente. Otras partes del programa que no dependan de la frecuencia podrían seguir compilando sin problemas.

Definir un valor incorrecto puede producir errores difíciles de detectar. Por ejemplo, si el microcontrolador realmente funciona a 8 MHz pero se define F_CPU=16000000UL, una llamada a _delay_ms(1000) no durará un segundo, sino aproximadamente medio segundo. De forma similar, si el microcontrolador trabaja a 16 MHz pero se define 8000000UL, el retardo será aproximadamente el doble de lo esperado.

Lo mismo ocurre con otros cálculos que dependen de la velocidad del reloj, como la configuración de temporizadores, la comunicación serie (UART), SPI o I²C. Si F_CPU no coincide con la frecuencia real del microcontrolador, estos periféricos pueden funcionar con errores o dejar de comunicarse correctamente.

Puede definirse tanto en el código fuente como en la línea de comandos. Ambas opciones son válidas, pero definirla desde la línea de comandos presenta una ventaja importante: el mismo archivo blink.c puede compilarse para distintas frecuencias sin modificar una sola línea del código. Basta con cambiar el valor del parámetro durante la compilación.

Por ejemplo: 

avr-gcc -mmcu=atmega328p -DF_CPU=8000000UL ...
avr-gcc -mmcu=atmega328p -DF_CPU=16000000UL ...

Esto resulta especialmente útil cuando un mismo programa debe ejecutarse en placas diferentes, algunas con el oscilador interno de 8 MHz y otras con un cristal externo de 16 MHz.

También conviene entender el significado del sufijo UL.

  • U significa Unsigned, es decir, un entero sin signo.
  • L significa Long, es decir, un entero largo.

En consecuencia, 16000000UL indica al compilador que el número 16000000 debe tratarse como una constante de tipo unsigned long. Esto evita problemas de desbordamiento y asegura que los cálculos realizados por las bibliotecas sean correctos.

Los sufijos pueden escribirse tanto en mayúsculas como en minúsculas. Por ejemplo, 16000000UL, 16000000Ul, 16000000uL y 16000000ul son equivalentes para el compilador. Sin embargo, por legibilidad y porque es la forma utilizada en la documentación de AVR-LibC y en la mayoría de los ejemplos, es recomendable escribir siempre 16000000UL.

En cambio, expresiones como 16MHz, 16Mhz, 16mhz, 16MHZ o cualquier otra variante similar no son válidas. El compilador espera un valor numérico que represente la frecuencia en hercios, no un texto con unidades. La forma correcta de expresar 16 MHz es 16000000UL.

Parámetro -Os

Esta opción solicita al compilador que optimice el programa para reducir su tamaño. La letra O corresponde a Optimization y la s significa size.

En los microcontroladores esta opción es muy utilizada porque la memoria Flash suele ser limitada. El compilador intenta generar un programa más pequeño sin modificar su comportamiento, eliminando instrucciones innecesarias y reorganizando el código cuando es posible.

Existen otros niveles de optimización, como -O0, -O1, -O2 y -O3, pero -Os suele ofrecer un buen equilibrio entre tamaño del programa y rendimiento, por lo que es una de las opciones más habituales en proyectos AVR.

Resultado de la compilación

Si el proceso termina correctamente, el producto obtenido será el archivo blink.elf.

La extensión .elf corresponde al formato Executable and Linkable Format (ELF), un formato estándar utilizado por numerosos compiladores y herramientas de desarrollo.

Este archivo contiene mucho más que el código máquina que ejecutará el microcontrolador. También almacena información sobre las distintas secciones del programa (como el código, las variables inicializadas y los datos constantes), la tabla de símbolos utilizada por el depurador, información para el enlazador y, si se compila con opciones de depuración, datos adicionales que permiten analizar el programa durante el desarrollo.

Salvo que se indique otra ruta, blink.elf se genera en el mismo directorio donde se ejecutó el comando avr-gcc.

Aunque el archivo ELF ya contiene el programa compilado, normalmente todavía no es el archivo que se graba directamente en el microcontrolador. En el siguiente paso se extraerá de él un archivo en formato Intel HEX, que es el que habitualmente utiliza avrdude para programar la memoria Flash del dispositivo.

GENERAR EL ARCHIVO HEX

avr-objcopy -O ihex blink.elf blink.hex

Una vez que el programa ha sido compilado, el resultado es un archivo blink.elf. Sin embargo, este todavía no es el archivo que normalmente se utiliza para programar el microcontrolador.

El siguiente paso consiste en generar un archivo en formato Intel HEX, que es el formato que entienden la mayoría de los programadores para microcontroladores AVR, como USBasp, y también herramientas de programación como avrdude.

Para realizar esta conversión se utiliza la herramienta avr-objcopy, que forma parte de la colección de utilidades GNU Binutils. Su función es extraer del archivo ELF únicamente la información necesaria para grabar el programa en la memoria Flash del microcontrolador.

Durante este proceso se descartan elementos que resultan muy útiles durante el desarrollo, como la información de depuración, la tabla de símbolos y otros metadatos utilizados por el compilador, el enlazador y los depuradores. El resultado es un archivo mucho más simple, que contiene únicamente los datos que deben escribirse en la memoria del dispositivo.

Parámetro -O ihex

La opción -O indica el formato de salida (Output format) que debe generar avr-objcopy. En este caso, el formato elegido es ihex, abreviatura de Intel HEX.

El formato Intel HEX no almacena la información como una secuencia de bytes binarios, sino como un archivo de texto formado por líneas de caracteres ASCII. Cada línea representa un registro que contiene información como la dirección de memoria donde deben grabarse los datos, la cantidad de bytes, los propios datos y un byte de verificación (checksum) que permite detectar errores de transmisión.

Gracias a esta estructura, el archivo puede abrirse con cualquier editor de texto. Aunque su contenido no resulta fácil de interpretar para una persona, sí puede comprobarse que está formado por caracteres ASCII y no por datos binarios.

Por ejemplo, una línea típica de un archivo Intel HEX puede verse así: 

:100000000C945C000C946E000C946E000C946E00A4

Cada uno de esos caracteres representa información codificada en formato hexadecimal que posteriormente será interpretada por el programador para grabar correctamente la memoria Flash del microcontrolador.

Esto suele generar cierta confusión. El programa que finalmente ejecutará el microcontrolador sí está formado por instrucciones binarias almacenadas en la memoria Flash. Sin embargo, antes de ser grabadas, esas instrucciones se representan mediante líneas de texto en formato Intel HEX para facilitar su almacenamiento, transporte y programación.

Dónde se genera el archivo .hex

En el comando anterior, el último argumento indica el nombre del archivo de salida: 

blink.hex

Salvo que se especifique otra ruta, este archivo se genera en el mismo directorio desde el cual se ejecutó el comando avr-objcopy. Es decir, si la compilación se realiza dentro de la carpeta del proyecto, allí aparecerá también el archivo blink.hex, junto al archivo blink.elf.

El nombre del archivo no está fijado por ninguna regla. En este ejemplo se llama blink.hex simplemente porque el programa se llama blink, pero podría haberse utilizado cualquier otro nombre, por ejemplo: 

avr-objcopy -O ihex blink.elf programa_final.hex

En ese caso, el archivo generado se llamaría programa_final.hex.

En resumen, el archivo blink.hex es una representación textual del contenido que debe escribirse en la memoria Flash del microcontrolador. Será el archivo que, en el siguiente paso, utilizaremos junto con avrdude y un programador como USBasp para transferir el programa al ATmega328P.

4. PROGRAMAR EL MICROCONTROLADOR

avrdude -c usbasp -p m328p -U flash:w:blink.hex

avrdude es la utilidad encargada de comunicarse con el programador y, a través de él, con el microcontrolador. Además de escribir la memoria Flash, también puede leer la EEPROM, consultar la firma del dispositivo y modificar los fusibles.

Significado de los parámetros

  • -c usbasp: selecciona el programador USBasp.
  • -p m328p: indica que el dispositivo es un ATmega328P.
  • -U flash:w:blink.hex: indica a avrdude qué operación debe realizar sobre la memoria del microcontrolador. Este parámetro está formado por tres partes separadas por dos puntos (:):
    • flash: especifica la memoria sobre la que se realizará la operación. En este caso, la memoria Flash, donde se almacena el programa que ejecutará el microcontrolador. También es posible operar sobre otras memorias, como la EEPROM o los fusibles (fuses).
    • w: indica la acción que se desea realizar. La letra w proviene de write (escribir) y ordena a avrdude grabar datos en la memoria seleccionada. Existen otras operaciones, como r (read, leer) o v (verify, verificar).
    • blink.hex: es el archivo que contiene el programa que será grabado en la memoria Flash. En el paso anterior generamos este archivo a partir de blink.elf mediante avr-objcopy. Durante la programación, avrdude lee su contenido y lo transfiere, a través del programador USBasp, a la memoria Flash del ATmega328P.

Una vez finalizada la grabación, el microcontrolador conserva el programa en su memoria Flash incluso aunque se desconecte la alimentación. Cuando vuelva a encenderse o se reinicie, comenzará a ejecutar el programa almacenado desde la dirección inicial de la memoria.

4. INTERPRETANDO LA SALIDA DE AVRDUDE

avrdude: AVR device initialized and ready to accept instructions
avrdude: device signature = 0x1e950f (probably m328p)
avrdude: erasing chip
avrdude: writing 156 bytes flash ...
avrdude: verifying flash memory against blink.hex
avrdude: 156 bytes of flash verified
avrdude done. Thank you.

Estos mensajes indican que la comunicación fue correcta, la firma del microcontrolador coincide con la esperada, la memoria Flash fue borrada, el programa se grabó correctamente y la verificación confirmó que los datos escritos coinciden exactamente con el archivo HEX.

5. EL AVISO «cannot set sck period»

Algunos USBasp antiguos muestran el mensaje cannot set sck period. Aunque aparece la palabra «error», normalmente solo indica que el firmware del programador no soporta el ajuste dinámico de la frecuencia SCK. Si posteriormente la memoria se escribe y verifica correctamente, el aviso puede ignorarse.

6. COMPROBAR EL TAMAÑO DEL PROGRAMA

avr-size blink.elf
text    data    bss    dec    hex
                156       0      0     156     9c

Esta información permite comprobar cuánta memoria Flash y SRAM utiliza el programa, algo muy importante cuando se trabaja con microcontroladores de recursos limitados.

RESUMEN

nano blink.c
avr-gcc -mmcu=atmega328p -DF_CPU=16000000UL -Os blink.c -o 
blink.elf 
avr-objcopy -O ihex blink.elf blink.hex 
avr-size blink.elf 
avrdude -c usbasp -p m328p -U flash:w:blink.hex

Comprender este flujo de trabajo ayuda a entender cómo un archivo de texto escrito en C termina convirtiéndose en un firmware que se ejecuta dentro del microcontrolador. Además, proporciona una base sólida para automatizar el proceso mediante scripts o Makefiles y facilita la resolución de problemas cuando algo no funciona como se esperaba.
