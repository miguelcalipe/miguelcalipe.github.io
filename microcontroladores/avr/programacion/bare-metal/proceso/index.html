PROCESO DE COMPILACIÓN Y PROGRAMACIÓN DE MICROCONTROLADORES AVR

1. Introducción

Para que un microcontrolador AVR pueda ejecutar un programa escrito en lenguaje C, el código fuente debe pasar por una serie de etapas antes de llegar a la memoria del dispositivo. El archivo que escribe el programador no es directamente ejecutable por la CPU del AVR.

En un entorno de programación Bare-Metal, este proceso se realiza mediante una cadena de herramientas (toolchain) que incluye el preprocesador, el compilador, el ensamblador, el enlazador y otras utilidades destinadas a generar el archivo que finalmente será programado en la memoria Flash.

En este artículo seguiremos el recorrido desde el código fuente en C hasta la programación del microcontrolador mediante herramientas de línea de comandos. El objetivo es comprender qué función cumple cada etapa y qué archivos se generan durante el proceso.

Como ejemplo utilizaremos un programa sencillo para un microcontrolador de la familia AVR: 

#include <avr/io.h>

int main(void)
{
DDRB |= (1 << PB0);
PORTB |= (1 << PB0);

while (1)
{
}

}

El programa configura el pin PB0 como salida y establece su nivel lógico en alto. El funcionamiento de los registros y del circuito de salida del pin se explica con mayor detalle en el artículo Del código C al pin físico: cómo un AVR controla una salida digital. Aquí nos concentraremos en el proceso necesario para transformar este código fuente en un firmware que pueda ser almacenado y ejecutado por el microcontrolador.

2. Del código fuente al firmware

El punto de partida es un archivo de código fuente, normalmente identificado con la extensión .c. Este archivo contiene instrucciones y declaraciones escritas en lenguaje C y puede incluir archivos de cabecera mediante directivas del preprocesador.

2.1. El archivo fuente en C

Podemos guardar nuestro programa, por ejemplo, en: 

main.c

En nuestro ejemplo aparece: 

#include <avr/io.h>

El archivo avr/io.h forma parte de avr-libc y proporciona las definiciones necesarias para trabajar con los registros y bits correspondientes al microcontrolador seleccionado.

De esta manera podemos utilizar nombres como: 

DDRB

PORTB
PB0

sin tener que escribir directamente en el programa las direcciones numéricas asociadas a los registros de hardware.

Estas definiciones son utilizadas durante la construcción del programa y no significan que la CPU del AVR ejecute directamente los nombres escritos en C. Durante las siguientes etapas, el código será transformado en instrucciones correspondientes a la arquitectura del dispositivo.

2.2. El preprocesador

Antes de que el compilador analice propiamente el lenguaje C, interviene el preprocesador.

El preprocesador procesa las directivas que comienzan con el carácter #, entre ellas #include, #define y determinadas estructuras condicionales.

En nuestro ejemplo: 

#include <avr/io.h>

Esta directiva hace que el contenido correspondiente del archivo de cabecera sea incorporado al resultado del preprocesamiento.

El resultado de esta etapa sigue siendo código fuente en C, pero con las directivas del preprocesador ya resueltas. 

main.c

│
▼
Preprocesador
│
▼
Código C preprocesado

En muchos casos el programador no necesita conservar este archivo intermedio, ya que las herramientas posteriores pueden recibirlo directamente como parte del proceso de compilación.

2.3. Compilación del código

El compilador analiza el código C y lo transforma en una representación que posteriormente podrá convertirse en instrucciones de la arquitectura AVR.

Cuando utilizamos la GNU AVR Toolchain, el compilador correspondiente a la arquitectura AVR es avr-gcc.

Un ejemplo de una orden de compilación es: 

avr-gcc -mmcu=atmega168 -Os -c main.c -o main.o

La opción -mmcu=atmega168 indica al compilador que el programa está destinado a un ATmega168.

Esta información es importante porque diferentes dispositivos AVR pueden disponer de distintas cantidades de memoria, periféricos, registros y características de arquitectura. La selección del dispositivo también permite que las definiciones proporcionadas por avr/io.h correspondan al microcontrolador seleccionado.

La opción -Os solicita al compilador optimizar el programa teniendo como objetivo reducir el tamaño del código generado. En microcontroladores con memoria de programa limitada, reducir el tamaño del firmware puede ser especialmente importante.

La optimización también puede modificar la forma en que el compilador genera las instrucciones. Por esta razón, el código máquina resultante no debe interpretarse como una traducción literal línea por línea del código C.

La opción -c indica que se debe compilar el archivo fuente y generar un archivo objeto, pero sin realizar todavía el enlazado final.

Finalmente, -o main.o especifica el nombre del archivo de salida. 

main.c

│
▼
avr-gcc
│
▼
main.o

2.4. Código ensamblador

El procesador del microcontrolador no ejecuta directamente el código C. Durante la compilación, el compilador genera instrucciones correspondientes a la arquitectura AVR.

Para estudiar el resultado de la compilación podemos solicitar al compilador que genere código ensamblador: 

avr-gcc -mmcu=atmega168 -Os -S main.c -o main.s

La opción -S hace que el proceso se detenga después de la generación del código ensamblador.

El archivo obtenido será: 

main.s

Este archivo permite observar de forma más cercana las instrucciones que posteriormente serán convertidas en código máquina.

Las instrucciones exactas pueden variar dependiendo del microcontrolador seleccionado, del compilador y de las opciones de optimización utilizadas.

Por ello, una expresión de C como: 

DDRB |= (1 << PB0);

no debe entenderse como una traducción obligatoria a una secuencia fija de instrucciones. El compilador puede utilizar diferentes estrategias para obtener el resultado funcional requerido.

2.5. Ensamblado y archivos objeto

El código ensamblador debe transformarse en código máquina. Esta tarea la realiza el ensamblador.

Dentro de la GNU AVR Toolchain, esta función forma parte de las herramientas utilizadas por avr-gcc.

El resultado es un archivo objeto, normalmente con extensión .o. Por ejemplo: 

main.o

Un archivo objeto contiene código máquina y otra información necesaria para completar posteriormente el programa durante la etapa de enlazado.

En un proyecto sencillo puede existir un único archivo objeto. En proyectos más grandes pueden existir varios: 

main.o
gpio.o
uart.o
timer.o

Estos archivos deben reunirse posteriormente para construir el programa completo.

2.6. Enlazado y archivo ELF

El enlazador (linker) combina los diferentes archivos objeto y determina cómo quedarán organizados dentro del espacio de memoria del microcontrolador.

En un proyecto sencillo podemos tener: 

main.o

mientras que un proyecto más complejo puede incluir varios archivos objeto y bibliotecas.

El enlazado produce normalmente un archivo en formato ELF (Executable and Linkable Format). 

main.elf

El archivo ELF contiene información mucho más completa que la necesaria para programar directamente la memoria Flash. Puede incluir las diferentes secciones del programa, direcciones, símbolos y otra información utilizada por las herramientas de desarrollo.

Una parte importante del trabajo del enlazador consiste en colocar las diferentes secciones del programa en las regiones de memoria correspondientes al dispositivo seleccionado.

2.7. Las secciones del programa

El programa final no consiste simplemente en una secuencia indiferenciada de bytes. El firmware contiene diferentes tipos de información que deben ubicarse en las regiones de memoria correspondientes.

2.7.1. Sección de código

La sección .text contiene principalmente las instrucciones que ejecutará la CPU. En un AVR, estas instrucciones se almacenan normalmente en la memoria Flash.

2.7.2. Datos inicializados

La sección .data contiene variables que tienen un valor inicial explícito y que requieren una organización particular durante el arranque del programa.

2.7.3. Datos no inicializados

La sección .bss se utiliza para variables que no necesitan tener un valor inicial almacenado en la imagen de programa.

La organización exacta de estas secciones depende de la arquitectura y de las reglas de enlace utilizadas por la toolchain.

3. Generación del archivo de programación

3.1. El archivo ELF

Una vez completado el enlazado, el archivo ELF contiene el programa preparado según el mapa de memoria del microcontrolador.

En esta etapa es posible utilizar herramientas como avr-size para conocer cuánto espacio ocupa el programa: 

avr-size main.elf

Esta información resulta especialmente útil cuando se trabaja con microcontroladores que disponen de una cantidad limitada de memoria Flash y RAM.

El archivo ELF también resulta útil durante la depuración, ya que conserva información que puede ser utilizada para relacionar direcciones de memoria con símbolos y partes del programa.

3.2. Generación del archivo HEX

El archivo ELF contiene información que no es necesaria para programar directamente la memoria Flash. Por ello se genera normalmente un archivo en un formato adecuado para la programación.

Una de las herramientas utilizadas para este propósito es avr-objcopy.

Un ejemplo es: 

avr-objcopy -O ihex -R .eeprom main.elf main.hex

En esta orden, -O ihex indica que el formato de salida será Intel HEX.

La opción -R .eeprom excluye la sección de EEPROM de este archivo HEX concreto. Esto permite generar una imagen destinada específicamente a la memoria de programa.

Como resultado obtenemos: 

main.hex

El archivo HEX contiene los datos y las direcciones necesarias para que una herramienta de programación pueda escribir el contenido correspondiente en la memoria del microcontrolador.

4. Programación del microcontrolador

Una vez generado el archivo HEX, todavía falta transferirlo al microcontrolador.

Para ello podemos utilizar un programador compatible con el AVR y una herramienta de programación como AVRDUDE.

AVRDUDE permite comunicarse con diferentes programadores y dispositivos AVR y realizar operaciones sobre sus memorias y registros de programación.

Por ejemplo, utilizando un programador USBasp: 

avrdude -c usbasp -p m168 -U flash:w:main.hex:i

4.1. Selección del programador

-c usbasp

indica que se utilizará un programador compatible con USBasp.

4.2. Selección del microcontrolador

-p m168

indica el dispositivo AVR que será programado.

El código utilizado por AVRDUDE debe corresponder al microcontrolador real conectado al programador.

4.3. Escritura de la memoria Flash

-U flash:w:main.hex:i

indica una operación sobre la memoria Flash.

La letra w especifica que se realizará una escritura (write), mientras que main.hex identifica el archivo que contiene los datos que serán programados.

La letra i indica que el archivo está en formato Intel HEX.

4.4. Verificación de la programación

Después de escribir el firmware en la memoria Flash, es importante verificar que los datos almacenados en el microcontrolador coincidan con los datos que se pretendían programar.

AVRDUDE puede realizar esta comprobación como parte del proceso de programación.

La verificación permite detectar problemas de comunicación entre el programador y el microcontrolador o errores durante la transferencia de los datos.

Por tanto, el proceso no debe entenderse simplemente como: 

archivo HEX → memoria Flash

sino como una operación de programación en la que también podemos comprobar que el contenido almacenado corresponde con la imagen que se pretendía escribir.

5. Ejecución del firmware

Una vez que el programa se encuentra almacenado en la memoria Flash, el microcontrolador puede comenzar a ejecutar las instrucciones.

En condiciones normales de funcionamiento, después de un reset, el AVR inicia la secuencia de arranque y comienza la ejecución del programa desde la dirección correspondiente.

El código que originalmente escribimos en C ya no existe en la Flash como instrucciones de C. Lo que se encuentra almacenado son los datos que representan las instrucciones y demás información necesaria para ejecutar el firmware.

Cuando la CPU ejecuta las instrucciones generadas a partir del programa, estas pueden modificar los registros de los periféricos y controlar el hardware interno del microcontrolador.

En nuestro ejemplo, la ejecución de las instrucciones relacionadas con DDRB y PORTB termina produciendo el comportamiento eléctrico correspondiente en PB0. Este recorrido desde las instrucciones hasta el pin físico se desarrolla en detalle en el artículo Del código C al pin físico: cómo un AVR controla una salida digital.

6. Herramientas de la GNU AVR Toolchain

Aunque habitualmente utilizamos avr-gcc como punto de entrada para construir un programa, detrás de esta herramienta existe una cadena de programas que participan en las diferentes etapas. 

avr-gcc

│
├── Preprocesador
│
├── Compilador
│
├── Ensamblador
│
└── Enlazador

Además, otras herramientas permiten inspeccionar y transformar los archivos generados: 

avr-size       → información sobre el tamaño del programa


avr-objcopy     → conversión de formatos
avr-objdump     → inspección del contenido del programa
avr-nm          → información sobre símbolos

Finalmente, AVRDUDE cumple una función diferente. No forma parte de la transformación del código C en instrucciones, sino que permite comunicarse con el programador y transferir el firmware al microcontrolador.

7. Compilar y programar: dos procesos diferentes

Es importante distinguir dos procesos que con frecuencia se confunden: compilar y programar.

Compilar significa transformar el código fuente y construir el programa ejecutable para la arquitectura del microcontrolador.

Programar el microcontrolador significa transferir ese programa a la memoria del dispositivo mediante una interfaz y un programador adecuados.

Por ejemplo: 

main.c

│
▼
Compilación y enlace
│
▼
main.elf
│
▼
Generación del HEX
│
▼
main.hex

Hasta este punto hemos construido el firmware, pero todavía no necesariamente lo hemos almacenado en el microcontrolador.

La siguiente etapa es: 

main.hex


│
▼
AVRDUDE
│
▼
Programador
│
▼
AVR
│
▼
Memoria Flash

Esta distinción es fundamental cuando se trabaja directamente desde la línea de comandos, porque permite identificar con precisión en qué etapa se encuentra un problema.

8. Recorrido completo del proceso

8.1. Código fuente

El programador escribe el firmware en lenguaje C en uno o varios archivos fuente.

8.2. Construcción del programa

La toolchain procesa el código mediante el preprocesador, el compilador, el ensamblador y el enlazador, produciendo un archivo ELF.

8.3. Generación de la imagen de programación

Las herramientas de la GNU AVR Toolchain pueden convertir el contenido necesario del ELF en un archivo Intel HEX.

8.4. Programación

AVRDUDE utiliza el programador conectado al AVR para transferir el contenido del archivo HEX a la memoria Flash.

8.5. Ejecución

Una vez programado y puesto en funcionamiento el microcontrolador, la CPU ejecuta las instrucciones almacenadas en la memoria de programa.

8.6. Relación con el hardware

A partir de la ejecución del firmware comienza la interacción entre la CPU, los registros y los periféricos del microcontrolador. Las instrucciones pueden modificar registros de entrada y salida y producir cambios en el comportamiento eléctrico de los circuitos internos y de los pines.

El recorrido desde las instrucciones ejecutadas hasta la señal eléctrica presente en un pin se desarrolla en el artículo Del código C al pin físico: cómo un AVR controla una salida digital.

9. Conclusión

Un programa escrito en C no pasa directamente desde el editor hasta la CPU del microcontrolador. Antes de ejecutarse debe atravesar una cadena de transformación en la que intervienen diferentes herramientas y formatos.

El proceso comienza con el archivo fuente y continúa con el preprocesamiento, la compilación, el ensamblado y el enlazado. El resultado es un archivo ELF que contiene el programa organizado de acuerdo con el dispositivo seleccionado.

Posteriormente, una herramienta como avr-objcopy permite generar una imagen en formato Intel HEX, que puede ser transferida al microcontrolador mediante AVRDUDE y el programador correspondiente.

Finalmente, el AVR ejecuta las instrucciones almacenadas en su memoria de programa. A partir de ese momento comienza la interacción entre la CPU, los registros y los periféricos del microcontrolador.

Comprender esta cadena resulta especialmente importante en la programación Bare-Metal, porque permite saber exactamente qué ocurre entre el momento en que se escribe una instrucción en C y el momento en que el microcontrolador comienza a ejecutarla.

El siguiente nivel de análisis consiste en estudiar qué ocurre dentro del AVR cuando esas instrucciones modifican directamente los registros de entrada y salida. Ese recorrido permite relacionar las instrucciones ejecutadas por la CPU con la lógica interna de los periféricos y, finalmente, con las señales eléctricas presentes en los pines del dispositivo.
