COMUNICACIÓN SERIAL Y E/S DIGITAL

1. INTRODUCCIÓN Y FUNDAMENTOS DEL PROYECTO

El código que analizamos a continuación es un clásico programa de prueba ("loopback"):

  • El microcontrolador recibe un carácter byte a byte a través de su interfaz serial (USART).
  • Reenvía inmediatamente ese mismo byte de vuelta a la terminal de la computadora.
  • Muestra simultáneamente el valor numérico del carácter en formato binario mediante 8 LEDs conectados a un puerto de salida, en este caso PORTB

2. EL CÓDIGO FUENTE PRINCIPAL (serialLoopback.c)

El siguiente código es el punto de entrada de la aplicación:

/*
  A simple test of serial-port functionality.
  Takes in a character at a time and sends it right back out,
  displaying the ASCII value on the LEDs.
*/

// ------- Preamble -------- //
#include <avr/io.h>
#include <util/delay.h>
#include "pinDefines.h"
#include "USART.h"

int main(void) {
    char serialCharacter;

    // -------- Inits --------- //
    LED_DDR = 0xff; /* set up LEDs for output */
    initUSART();
    printString("Hello World!\r\n"); /* to test */

    // ------ Event loop ------ //
    while (1) {
        serialCharacter = receiveByte();
        transmitByte(serialCharacter);
        LED_PORT = serialCharacter;
        /* display ascii/numeric value of character */
    } /* End event loop */

    return (0);
}

3. Arquitectura de Archivos: ¿Por qué existen archivos .h y .c?

Para entender cómo estructurar un proyecto en C para microcontroladores, es fundamental comprender la diferencia entre declaración e implementación:

A. Archivos de Cabecera (.h)

Sirven exclusivamente para declarar qué funciones, macros o estructuras existen. Le dicen al compilador: "Confía en que estas funciones existen y tienen esta forma".

  • pinDefines.h: Contiene únicamente macros de preprocesador (#define). Al ser solo sustituciones de texto para mapear nombres (por ejemplo, transformar LED_PORT en PORTD), no genera código máquina por sí mismo, por lo que no lleva ni necesita un archivo pinDefines.c.
  • USART.h: Contiene los prototipos de las funciones de comunicación (por ejemplo, void initUSART(void);).

B. Archivos de Implementación (.c)

Contienen el código real y ejecutable que manipula los registros de hardware del microcontrolador.

  • USART.c: Es el archivo obligatorio que contiene la lógica interna de cómo se configuran los registros de baudios (UBRR), control (UCSR0A/B/C) y datos (UDR0) del USART.
Si se incluye una cabecera como #include "USART.h", el compilador sabrá usar las funciones, pero si olvidamos compilar y enlazar el archivo fuente USART.c, el enlazador (linker) fallará con un error de referencia indefinida (undefined reference).

Por lo tanto en este proyecto, para programar el microcontrolador debemos tener en la carpeta local no solo el archivo serialLoopback.c con el código fuente principal, también debemos tener los archivos de cabecera declarados pinDefines.h, USART.h y el archivo de implementación USART.c.

4. Desglose Lógico del Programa por Bloques

4.1. Preámbulo y Cabeceras


#include <avr/io.h>
#include <util/delay.h>
#include "pinDefines.h"
#include "USART.h"
  • <avr/io.h>: Es la cabecera fundamental de AVR-GCC. Al compilar para un microcontrolador específico (por ejemplo, el ATmega88PA), este archivo mapea los nombres simbólicos de los registros (como DDRB o PORTD) a sus direcciones físicas de memoria RAM/I/O correspondientes.
  • <util/delay.h>: Provee rutinas de retardo por software basadas en ciclos de reloj (_delay_ms, _delay_us). Aunque no se usa de forma explícita dentro del main en este ejemplo, suele incluirse por estandarización en las plantillas de proyectos iniciales.
  • "pinDefines.h" y "USART.h": Al entrecomillarlo, se le está indicando al compilador que esos archivos no forman parte de la librería estándar del sistema, sino que son archivos locales del proyecto. El primero abstrae los nombres físicos de los pines y puertos (traduciendo LED_DDR y LED_PORT al puerto real, como DDRB y PORTB). El segundo encapsula la configuración de los registros del USART (baud rate, habilitación de TX/RX, formato de trama).

4.2. Inicialización (Inits)

  • Configuración del puerto de LEDs: LED_DDR = 0xff;: Configura el puerto de los LEDs como salida completa escribiendo unos (0xff) en el registro de dirección de datos. Esto configura los 8 pines del puerto como salidas digitales, preparándolos para drenar o suministrar corriente a los LEDs.
  • Inicialización serial: initUSART(); y printString(...): Configuran el hardware USART interno del microcontrolador y envían un mensaje inicial de prueba a la terminal. Esto implica programar los registros UBRR (baud rate register), UCSR0A, UCSR0B y UCSR0C para establecer la velocidad de transmisión (por ejemplo, 9600 baudios), el tamaño de palabra (8 bits), sin paridad y 1 bit de parada.
  • Mensaje de prueba: printString("Hello World!\r\n"); envía una cadena de caracteres byte por byte a través del transmisor UART. La secuencia \r\n asegura el retorno de carro y el avance de línea en la consola de la PC.

4.3. El Bucle Infinito (Event Loop)

while (1) {
serialCharacter = receiveByte();
transmitByte(serialCharacter);
LED_PORT = serialCharacter;
}

Una vez inicializado el sistema, el microcontrolador entra en un ciclo cerrado de ejecución (Super Loop):

  • Recepción (receiveByte()): Esta función se queda bloqueada (esperando activamente) hasta que el búfer de recepción del UART (UDR) recibe un nuevo byte proveniente de la computadora. Una vez completada la recepción, el valor se almacena en la variable serialCharacter.
  • Transmisión (transmitByte(serialCharacter);): Inmediatamente toma el byte recibido y lo retransmite hacia el puerto serie. Esto genera el efecto de eco (echo) en la terminal.
  • Reflejo en Hardware (LED_PORT = serialCharacter;): Asigna el valor del carácter recibido directamente al registro de salida del puerto (PORTD o PORTB). Como cada bit del puerto controla un LED, el número ASCII del carácter se visualiza instantáneamente en binario. Por ejemplo, si presionas la tecla A (código ASCII 65 decimal, 01000001 en binario), los LEDs encenderán exactamente en esa esa combinación de bits.

5. Proceso de Compilación y Enlazado

Para generar el archivo ejecutable para el ATmega88PA a una frecuencia de reloj de 8 MHz, se debe compilar el archivo principal junto con la implementación real del USART

Durante esta fase, pinDefines.h es procesado por el compilador para resolver las macros antes de traducir el código fuente a lenguaje de máquina. El flujo completo de compilación mediante la cadena de herramientas GNU se realiza con los siguientes comandos:

5.1. Compilación en dos pasos

Los dos comandos con la bandera -c hacen algo específico: compilan cada archivo fuente por separado y generan archivos objeto (.o). El beneficio principal es la escalabilidad (compilación incremental): En un proyecto grande con decenas de archivos, si modificas una sola línea en main.c, no quieres perder tiempo volviendo a compilar todo el código de librerías como USART.c. Con los archivos objeto, solo vuelves a compilar el archivo que cambiaste y al final ejecutas el enlazador. Para un proyecto pequeño de dos archivos, puede parecer innecesario


# 1. Compilar el archivo principal. 
avr-gcc -Os -DF_CPU=8000000UL -mmcu=atmega88pa -c serialLoopback.c -o serialLoopback.o

# 2. Compilar el archivo del USART 
avr-gcc -Os -DF_CPU=8000000UL -mmcu=atmega88pa -c USART.c -o USART.o

# 3. Enlazar los objetos para generar el ejecutable .elf
avr-gcc -mmcu=atmega88pa serialLoopback.o USART.o -o serialLoopback.elf

# 4. Extraer el formato Intel Hex para flasheo
avr-objcopy -j .text -j .data -O ihex serialLoopback.elf serialLoopback.hex

Para entender el flujo completo, así es como interactúan los cuatro comandos:

  1. avr-gcc ... -c serialLoopback.c -o serialLoopback.o
    Compila tu archivo principal y genera un archivo binario intermedio llamado serialLoopback.o. La bandera -c: compile only (solo compilar) le indica al compilador que traduzca el archivo de código fuente en C (.c) a código de máquina, pero que no ejecute la fase de enlazado (linking). El resultado es un archivo objeto intermedio con extensión .o. Este archivo .o contiene el código traducido, pero todavía no sabe dónde están las funciones de otros archivos (como las del USART.c). La bandera -c permite compilar cada archivo fuente de forma independiente antes de unirlos en un solo paso posterior.
  2. avr-gcc ... -c USART.c -o USART.o
    Compila el archivo de la librería serial y genera un archivo intermedio llamado USART.o.
  3. avr-gcc -mmcu=atmega88pa serialLoopback.o USART.o -o serialLoopback.elf
    El Enlazador (Linker). Toma los dos archivos .o anteriores, los une, resuelve las referencias cruzadas (conecta las llamadas a initUSART y receiveByte con el código real que las implementa) y genera un archivo ejecutable unificado llamado serialLoopback.elf.
  4. avr-objcopy -j .text -j .data -O ihex serialLoopback.elf serialLoopback.hex
    Toma el archivo .elf, extrae exclusivamente las secciones de código y datos (-j), y las convierte a formato estándar Intel Hex (-O ihex), resultando en el archivo serialLoopback.hex que finalmente se flasheará en el microcontrolador.

5.2. Compilación en un solo paso directo

Si quieres hacerlo de forma rápida desde la terminal ejecutando una sola línea antes del flasheo, puedes combinar la compilación y el enlazado directamente: 


# 1. Compilar y enlazar todo en un solo comando
avr-gcc -mmcu=atmega88pa -DF_CPU=8000000UL -Os serialLoopback.c USART.c -o serialLoopback.elf

# 2. Extraer el archivo .hex
avr-objcopy -j .text -j .data -O ihex serialLoopback.elf serialLoopback.hex

Es totalmente válido, correcto y mucho más cómodo para proyectos pequeños o pruebas rápidas. Lo que hace avr-gcc bajo el capó cuando le pasas varios archivos .c juntos es compilar cada uno en memoria de manera temporal y enlazarlos de inmediato en un solo paso, entregándote el archivo .elf listo.

Una vez ejecutado cualquiera de estos dos métodos, tendrás listo tu archivo serialLoopback.hex para enviarlo al microcontrolador con avrdude.

Técnicamente, también se puede usar un comando simplificado para extraer el archivo .hex y funcionará en la gran mayoría de los casos para proyectos básicos de microcontroladores AVR:

avr-objcopy -O ihex serialLoopback.elf serialLoopback.hex

Diferencia prática

  1. Con -j .text -j .data (Forma estricta) le indicas explícitamente a avr-objcopy que filtre y extraiga únicamente las secciones de código ejecutable (.text) y datos inicializados (.data). Cualquier sección de depuración o metadatos generada por el compilador es descartada automáticamente. Se utiliza por seguridad y control estricto del espacio. En sistemas embebidos, la memoria Flash es muy limitada. Especificar exactamente qué secciones se van a grabar garantiza que ningún byte sobrante o metadato de depuración termine flotando en el archivo .hex que se enviará al microcontrolador.
  2. En la Forma directa, avr-objcopy toma todo el archivo .elf y traduce a formato Intel Hex casi todo lo que encuentra (excluyendo por defecto secciones de depuración puras conocidas como no cargables, pero conservando tablas de símbolos o secciones especiales si estuvieran presentes). Para un programa sencillo como serialLoopback, ambas opciones generan exactamente el mismo resultado práctico en la memoria Flash del ATmega88PA

6. PROGRAMACIÓN DEL MICROCONTROLADOR

Una vez obtenido el archivo serialLoopback.hex, los archivos de código fuente y cabeceras ya cumplieron su propósito. El archivo binario se transfiere a la memoria Flash del ATmega88PA mediante un programador ISP (como un USBasp).

para el flasheo del microcontrolador ATmega88PA utilizando un programador USBasp, existen una forma extendida (que incluye opciones de seguridad y configuración de fusibles o verificación) y una forma breve (la instrucción mínima indispensable).

6.1. Forma breve (comando directo)

Es la instrucción mínima necesaria para tomar el archivo .hex y grabarlo directamente en la memoria Flash del microcontrolador. Se usa en pruebas rápidas del día a día en la mesa de trabajo cuando ya se sabe que el hardware y los fusibles están configurados correctamente.


avrdude -c usbasp -p m88p -U flash:w:serialLoopback.hex
  • -mmcu=atmega88pa: Define la arquitectura del microcontrolador.
  • -DF_CPU=8000000UL: Establece la frecuencia de reloj para calcular los retardos y velocidades de baudios.
  • -Os: Optimiza el código para reducir el tamaño en la memoria Flash.
  • serialLoopback.c USART.c: Compila y une ambos módulos de código fuente para evitar errores de enlace.

6.2. La forma extendida (Con verificación y control de memoria)

Agrega parámetros adicionales para garantizar la integridad del proceso y consultar el estado del chip: 


avrdude -c usbasp -p m88p -v -U flash:w:serialLoopback.hex:i
  • -v(Verbose): Muestra información detallada en pantalla durante todo el proceso de comunicación con el programador (muy útil para depurar si hay falsos contactos en los pines ISP)
  • :i (al final de la ruta del archivo): Especifica explícitamente el formato del archivo que se va a escribir (i de Intel Hex). Aunque avrdude suele adivinarlo por la extensión .hex, declararlo de forma explícita evita ambigüedades en scripts automatizados.
  • -Os: Optimiza el código para reducir el tamaño en la memoria Flash.
