SISTEMAS EMBEBIDOS Y PROCESAMIENTO EN TIEMPO REAL

INTRODUCCIÓN

Un sistema embebido está diseñado para realizar una función determinada dentro de un equipo o sistema mayor. Para cumplir esa función no basta con que el procesador sea capaz de ejecutar instrucciones. En muchas aplicaciones, además, debe hacerlo dentro de determinados límites de tiempo.

Esta característica introduce uno de los conceptos fundamentales de los sistemas embebidos: el procesamiento en tiempo real.

Un sistema de tiempo real es aquel cuyo funcionamiento depende no solo de producir un resultado correcto, sino también de producirlo dentro del intervalo de tiempo establecido por la aplicación. El sistema debe responder a eventos, procesar información y, cuando corresponda, controlar elementos externos dentro de los plazos requeridos.

Los sistemas embebidos están frecuentemente sujetos a restricciones temporales y deben responder a secuencias y combinaciones de eventos. Además, una misma aplicación puede tener que realizar varias actividades, algunas periódicas y otras desencadenadas por eventos.

En este artículo se desarrolla el concepto de tiempo real desde una perspectiva general, aplicable a sistemas embebidos basados en diferentes microcontroladores y arquitecturas.

1. EL PROCESAMIENTO EN TIEMPO REAL

1.1. Resultado correcto y respuesta dentro del tiempo requerido

En un sistema convencional, normalmente interesa que una operación termine correctamente. En un sistema de tiempo real, además de obtener el resultado correcto, el resultado debe estar disponible dentro del tiempo establecido.

Esta diferencia es fundamental.

Supongamos que un sistema mide una variable y debe actuar sobre ella. Si el procesamiento tarda demasiado, el resultado puede llegar cuando ya no resulta útil para controlar el sistema.

Por tanto, el funcionamiento correcto depende de dos condiciones:

Resultado correcto + respuesta dentro del tiempo requerido

La restricción temporal no significa necesariamente que el sistema tenga que ser extremadamente rápido. Significa que debe ser capaz de responder dentro del intervalo requerido por la aplicación.

Esta distinción es importante:

Velocidad de procesamiento y tiempo real no son conceptos equivalentes.

Un procesador puede ser muy rápido y, sin embargo, formar parte de un sistema que no garantiza los tiempos requeridos. Del mismo modo, un microcontrolador relativamente sencillo puede satisfacer perfectamente las necesidades de una aplicación si su carga de trabajo y sus restricciones temporales son moderadas.

1.2. Restricciones temporales y plazo máximo

Una aplicación embebida puede establecer un tiempo máximo para completar una determinada operación. Este límite puede denominarse plazo o deadline.

Por ejemplo, si un evento ocurre en un instante determinado, el sistema puede necesitar procesarlo antes de que ocurra el siguiente evento.

Si el procesamiento termina dentro del intervalo requerido, el sistema cumple su restricción temporal.

Si termina después, aunque el cálculo sea matemáticamente correcto, la respuesta puede dejar de ser válida para la aplicación.

Esto es especialmente importante en sistemas de:

  • control;
  • adquisición de datos;
  • comunicaciones;
  • procesamiento de señales;
  • supervisión;
  • automatización.

1.3. Tiempo de respuesta y latencia

El tiempo de respuesta es el intervalo que transcurre entre la aparición de un evento y la producción de la respuesta correspondiente.

Evento
  │
  │ t0
  ▼
┌─────────────────────────────┐
│        Procesamiento        │
└─────────────────────────────┘
  │
  │ t1
  ▼
Respuesta

Por tanto:

Tiempo de respuesta = t1 − t0

En una implementación real, este tiempo puede incluir varias etapas: detección del evento, atención del periférico, entrada a una rutina de interrupción, procesamiento de datos y actualización de una salida.

Por ello, también resulta importante el concepto de latencia, entendido como el tiempo que transcurre desde que ocurre un evento hasta que el sistema comienza a atenderlo o produce la respuesta correspondiente, según el contexto.

El tiempo disponible puede depender de factores como:

  • frecuencia de los eventos;
  • cantidad de datos que deben procesarse;
  • complejidad del algoritmo;
  • frecuencia de reloj del procesador;
  • actividades concurrentes;
  • acceso a memoria;
  • atención de interrupciones;
  • operaciones de entrada y salida;
  • comportamiento de los periféricos.

No todos estos factores tienen el mismo peso en todos los sistemas. El análisis debe realizarse para la aplicación concreta.

2. EVENTOS, PERIODICIDAD Y ACTIVIDADES CONCURRENTES

2.1. Eventos en un sistema embebido

Los sistemas embebidos suelen trabajar reaccionando a eventos.

Un evento puede proceder de:

  • un sensor;
  • una entrada digital;
  • un temporizador;
  • una interfaz de comunicación;
  • otro periférico;
  • una condición interna del sistema.

Los sistemas embebidos deben responder rápidamente a secuencias y combinaciones de eventos.

Sensor ───────┐
              │
Temporizador ─┼──► Sistema embebido ───► Respuesta
              │
Comunicación ─┘

El sistema recibe información de diferentes fuentes y debe procesarla de acuerdo con las reglas de la aplicación.

2.2. Procesamiento periódico

Una característica habitual de los sistemas embebidos es que algunas tareas se ejecutan periódicamente.

Una tarea periódica se ejecuta a intervalos determinados.

T0       T1       T2       T3       T4
│        │        │        │        │
▼        ▼        ▼        ▼        ▼
●        ●        ●        ●        ●

Cada punto representa una ejecución de la tarea.

Un temporizador puede utilizarse para establecer estos intervalos. Por ejemplo, una tarea podría ejecutarse cada 1 ms, 10 ms o 100 ms, dependiendo de los requisitos de la aplicación.

2.3. Procesamiento por eventos

En otros casos, la tarea se ejecuta cuando ocurre una condición determinada:

───────────────┬───────────────────────┬──────► tiempo
               │                       │
             Evento                  Evento
               │                       │
               ▼                       ▼
             Acción                  Acción

Un sistema real puede combinar ambos mecanismos.

Por ejemplo, puede ejecutar una tarea de supervisión periódicamente y, al mismo tiempo, responder a la llegada de un dato mediante una interrupción.

2.4. Varias actividades dentro de un mismo sistema

Un sistema embebido puede tener que realizar varias actividades:

┌───────────────────────────────────────┐
│ Sistema embebido                      │
│                                       │
│  Leer sensores                        │
│  Procesar datos                       │
│  Controlar salidas                    │
│  Gestionar comunicaciones             │
│  Supervisar el sistema                │
│                                       │
└───────────────────────────────────────┘

El material de Arm señala que los sistemas embebidos típicamente deben realizar múltiples actividades separadas al mismo tiempo.

Aquí conviene precisar el significado de "al mismo tiempo".

En un microcontrolador con un único núcleo de CPU, las instrucciones no se ejecutan literalmente de forma simultánea. El procesador alterna entre diferentes actividades según la organización del software, las interrupciones y los eventos que recibe.

Esto se denomina concurrencia: varias actividades pueden estar activas dentro del sistema y recibir atención durante determinados intervalos, aunque la CPU ejecute físicamente una secuencia de instrucciones.

Tiempo ─────────────────────────────────►

Tarea A: ███       ███       ███

Tarea B:    ██  ██    ██  ██

Tarea C:       ███          ███

El resultado es un sistema que atiende varias funciones dentro de una misma aplicación.

En procesadores multinúcleo, además, algunas actividades pueden ejecutarse realmente en paralelo en diferentes núcleos. Sin embargo, la concurrencia y la gestión temporal siguen siendo conceptos fundamentales.

3. TEMPORIZADORES E INTERUPCIONES COMO MECANISMOS DE TIEMPO REAL

3.1. Temporizadores

Los temporizadores son periféricos especialmente importantes en sistemas embebidos porque permiten establecer referencias temporales y generar eventos periódicos.

Pueden utilizarse, por ejemplo, para:

  • ejecutar tareas periódicamente;
  • medir intervalos de tiempo;
  • generar señales;
  • establecer tiempos de espera;
  • controlar la frecuencia de determinadas operaciones.

La utilización de un temporizador permite que el software no dependa exclusivamente de bucles de espera para controlar el tiempo.

3.2. Interrupciones como mecanismo de respuesta

Las interrupciones constituyen uno de los mecanismos fundamentales para responder a eventos.

En lugar de que el programa tenga que comprobar continuamente el estado de cada dispositivo, un periférico puede generar una solicitud de interrupción cuando ocurre una condición determinada.

Por ejemplo:

Temporizador
     │
     │ evento
     ▼
Interrupción
     │
     ▼
   CPU
     │
     ▼
Rutina de servicio
     │
     ▼
Continuación del programa

Este mecanismo permite que el procesador responda a determinados acontecimientos sin mantener necesariamente una espera activa permanente.

La utilización de interrupciones introduce, sin embargo, nuevas consideraciones temporales. La CPU puede estar ejecutando otra actividad cuando llega una interrupción y, por tanto, existe un tiempo de latencia antes de atenderla. Además, una rutina de servicio demasiado larga puede retrasar otras actividades.

Por ello, el diseño de interrupciones debe considerar tanto la prioridad de los eventos como el tiempo necesario para atenderlos.

3.3. Relación entre temporizadores, interrupciones y CPU

Los conceptos anteriores pueden relacionarse de la siguiente manera:

            Temporizador
                  │
                  ▼
                Evento
                  │
                  ▼
             Interrupción
                  │
                  ▼
                 CPU
                  │
          ┌───────┴────────┐
          │                │
          ▼                ▼
       Procesar         Decidir
          │                │
          └───────┬────────┘
                  ▼
              Periférico
                  │
                  ▼
               Actuador

Los GPIO y otros periféricos permiten recibir información del exterior y producir respuestas.

Esta relación será especialmente importante cuando se estudie la programación de microcontroladores a nivel de registros, bibliotecas o frameworks.

4. DIFERENTES NIVELES DE EXIGENCIA EN TIEMPO REAL

4.1. El tiempo real no significa solamente rapidez

Este es uno de los conceptos que más fácilmente puede confundirse.

Un procesador rápido puede ejecutar muchas instrucciones en poco tiempo, pero eso no garantiza por sí mismo que un sistema cumpla sus restricciones de tiempo real.

El requisito fundamental puede expresarse como:

Tiempo de respuesta del sistema
              ≤
Tiempo máximo permitido

Aumentar la velocidad del procesador puede ayudar, pero no es la única consideración.

También importan:

  • cantidad de trabajo que debe realizarse;
  • organización del software;
  • gestión de interrupciones;
  • operaciones de entrada y salida;
  • acceso a memoria;
  • otras tareas que estén ejecutándose;
  • comportamiento temporal de los periféricos.

Por eso, el diseño de un sistema de tiempo real debe considerar el comportamiento temporal del sistema completo y no solamente la frecuencia de reloj de la CPU.

4.2. Una computadora para bicicleta

El material de Arm utiliza como ejemplo una computadora para bicicleta y la caracteriza como un sistema de tiempo real débil.

El sistema mide la rotación de la rueda y calcula valores como:

  • velocidad;
  • distancia;
  • tiempo.

En este caso, el sistema debe procesar las señales provenientes del sensor con suficiente rapidez para mantener actualizados los valores mostrados.

El material señala que el procesamiento de la entrada puede realizarse entre dos impulsos del sensor sin algoritmos complejos. Esto permite utilizar un microcontrolador sencillo y de bajo costo.

El ejemplo permite observar una relación importante:

Requisito temporal
        │
        ▼
Carga de procesamiento
        │
        ▼
Capacidad necesaria del MCU

El microcontrolador debe seleccionarse en función de los requisitos reales de la aplicación.

4.3. Una unidad de control del motor

Existen aplicaciones en las que las restricciones temporales son mucho más exigentes.

El material de Arm presenta como ejemplo una unidad de control del motor de un automóvil. En este caso, los tiempos de encendido e inyección de combustible deben calcularse en tiempo real para que el motor funcione correctamente.

Cada cálculo debe terminar dentro de un instante definido.

Además de las restricciones temporales, esta aplicación presenta otras exigencias:

  • numerosos sensores;
  • actuadores;
  • comunicaciones con otros sistemas del vehículo;
  • funcionamiento en condiciones ambientales exigentes;
  • confiabilidad;
  • limitaciones de espacio;
  • necesidad de un costo razonable.

Por esta razón, el material concluye que se necesita un microcontrolador potente, confiable y de alto rendimiento.

4.4. Comparación de los dos ejemplos

Los ejemplos de la computadora para bicicleta y la unidad de control del motor permiten observar que "tiempo real" no describe un único nivel de exigencia.

Característica Computadora para bicicleta Control del motor
Entrada principal Rotación de rueda Múltiples sensores
Procesamiento Relativamente sencillo Más exigente
Restricción temporal Menos estricta Estricta
Cálculos Velocidad, distancia, tiempo Control del funcionamiento del motor
Actuadores Aplicación sencilla Numerosos actuadores
Confiabilidad Moderada Elevada
MCU Sencillo Mayor capacidad

La comparación procede de los ejemplos utilizados por Arm.

Lo importante no es determinar cuál sistema es "mejor", sino comprender que los requisitos de la aplicación determinan las características que debe tener el sistema embebido.

5. SISTEMAS DE CONTROL Y FUNCIONAMIENTO AUTÓNOMO

5.1. Sistemas de control de lazo cerrado

Los sistemas embebidos también pueden utilizarse como sistemas de control.

Un sistema de control de lazo cerrado supervisa el estado de un proceso y modifica una salida para mantener una determinada referencia, como temperatura, velocidad o dirección.

El principio puede representarse así:

                Referencia
                     │
                     ▼
                 ┌───────┐
                 │Control│
                 └───┬───┘
                     │
                     ▼
                  Salida
                     │
                     ▼
                  Sistema
                     │
                     ▼
                   Sensor
                     │
                     │ realimentación
                     └──────────────► Control

El controlador recibe información del proceso, la procesa y modifica una salida.

En este tipo de sistema, el tiempo puede ser una parte fundamental del funcionamiento. Si la medición o la acción de control se realizan demasiado tarde, el comportamiento del sistema puede verse afectado.

Por tanto, el procesamiento temporal no es un aspecto independiente del control: forma parte de la capacidad del sistema para reaccionar adecuadamente ante los cambios del proceso.

5.2. Funcionamiento autónomo

Muchos sistemas embebidos están diseñados para funcionar durante largos períodos sin intervención directa de un operador.

Esta autonomía implica que el sistema debe ser capaz de:

  • ejecutar su programa;
  • procesar entradas;
  • controlar salidas;
  • responder a eventos;
  • detectar determinadas condiciones anormales;
  • continuar funcionando dentro de sus condiciones previstas.

Esto diferencia a muchos sistemas embebidos de aplicaciones en las que existe una interacción constante con una persona.

Un sistema autónomo debe, por tanto, incorporar en su diseño no solamente las funciones normales, sino también mecanismos que permitan supervisar su propio funcionamiento.

6. GESTIÓN DE FALLOS Y DIAGNÓSTICO

6.1. Gestión de fallos

Un sistema que debe funcionar durante largos períodos no puede depender exclusivamente de que todo funcione correctamente en todo momento.

Arm señala que los sistemas embebidos deben poder manejar fallos sin bloquearse o colapsar y que, en determinados sistemas, el código destinado al manejo de fallos puede ser incluso más grande y complejo que el código correspondiente al funcionamiento normal.

Esto tiene una consecuencia directa sobre el diseño del software.

No basta con definir:

Funcionamiento normal
        │
        ▼
      Acción

También es necesario considerar condiciones anormales:

                ┌── Funcionamiento normal ──► Acción
                │
Evento ─────────┤
                │
                └── Condición anormal ─────► Manejo del fallo

La respuesta concreta ante un fallo depende del sistema.

Puede consistir en:

  • registrar una condición;
  • reiniciar una parte del sistema;
  • pasar a un estado seguro;
  • desactivar una función;
  • informar del problema;
  • continuar con las funciones que todavía sean posibles.

No existe una estrategia universal. El comportamiento debe definirse según los requisitos de la aplicación.

6.2. Diagnóstico del sistema

El manejo de fallos está relacionado con otra función importante: el diagnóstico.

Arm señala que los sistemas embebidos realizan funciones de diagnóstico para ayudar al personal de servicio a determinar rápidamente dónde se encuentra un problema.

El diagnóstico permite obtener información sobre el estado del sistema.

                Sistema embebido
                       │
            ┌──────────┴──────────┐
            │                     │
      Funcionamiento          Diagnóstico
         normal                  │
                                 ▼
                          Información de estado
                                 │
                                 ▼
                           Mantenimiento

La información de diagnóstico puede ser especialmente importante cuando el sistema está instalado dentro de un equipo donde el acceso al hardware es difícil.

Un diseño profesional debe considerar desde el principio cómo se detectarán, registrarán y comunicarán las condiciones anormales.

7. DISEÑO DE UN SISTEMA EMBEBIDO CON RESTRICCIONES TEMPORALES

7.1. Identificación de los requisitos

Antes de seleccionar un microcontrolador, es necesario conocer qué debe hacer el sistema.

Un procedimiento básico consiste en identificar:

Funciones
Determinar qué operaciones debe realizar el sistema.

Entradas
Determinar qué señales o datos recibirá.

Salidas
Determinar qué elementos deberá controlar.

Eventos
Identificar qué condiciones requieren una respuesta.

Tiempos
Determinar cuánto tiempo existe disponible para responder.

Carga de procesamiento
Estimar cuánto procesamiento requiere cada actividad.

Confiabilidad
Determinar qué debe ocurrir cuando aparece una condición anormal.

Recursos
Determinar la memoria, periféricos, interfaces y capacidad de procesamiento necesarias.

7.2. De los requisitos al microcontrolador

El proceso puede resumirse así:

Requisitos del sistema
          │
          ▼
Funciones y eventos
          │
          ▼
Restricciones temporales
          │
          ▼
Carga de procesamiento
          │
          ▼
Recursos hardware
          │
          ▼
Microcontrolador adecuado

Este proceso evita seleccionar un dispositivo únicamente por su frecuencia de reloj o por la cantidad de bits de su CPU.

La selección debe considerar el conjunto de requisitos: capacidad de procesamiento, memoria, periféricos, temporizadores, interrupciones, comunicaciones, consumo, costo, condiciones de funcionamiento y comportamiento temporal.

7.3. El tiempo real como característica del sistema completo

Un punto especialmente importante es que el comportamiento en tiempo real no depende exclusivamente del microcontrolador.

El sistema completo puede incluir:

  • hardware;
  • sensores;
  • actuadores;
  • microcontrolador;
  • memoria;
  • periféricos;
  • software;
  • comunicaciones;
  • alimentación;
  • elementos mecánicos, cuando corresponda.

Por tanto, el tiempo que transcurre entre un evento físico y una respuesta del sistema puede incluir diferentes etapas:

Evento físico
     │
     ▼
Sensor
     │
     ▼
Entrada del MCU
     │
     ▼
Periférico
     │
     ▼
CPU
     │
     ▼
Software
     │
     ▼
Periférico de salida
     │
     ▼

     │
     ▼
Respuesta física

Cada etapa puede introducir un tiempo determinado.

Por ello, afirmar que un microcontrolador es "rápido" no es suficiente para determinar si una aplicación cumple sus requisitos de tiempo real.

7.4. Verificación de los requisitos temporales

Una vez diseñado el sistema, los requisitos temporales deben comprobarse mediante análisis y mediciones.

Por ejemplo, si una tarea debe terminar como máximo en 2 ms, no basta con suponer que el microcontrolador es suficientemente rápido. Es necesario analizar el peor caso razonable de ejecución y comprobar que el sistema mantiene el tiempo requerido incluso cuando existen otras actividades, interrupciones y operaciones de entrada y salida.

Este enfoque lleva a una idea fundamental de la ingeniería de sistemas embebidos:

Los requisitos temporales deben especificarse, analizarse y verificarse; no deben suponerse.

8. RESUMEN TÉCNICO

Un sistema embebido puede estar sujeto a restricciones de tiempo real, lo que significa que determinadas operaciones deben producir una respuesta dentro de un intervalo establecido.

El tiempo real no significa simplemente ejecutar instrucciones rápidamente. Lo importante es que el sistema produzca la respuesta dentro del tiempo requerido por la aplicación.

Los sistemas embebidos pueden:

  • procesar tareas periódicas;
  • responder a eventos;
  • gestionar varias actividades concurrentes;
  • utilizar temporizadores;
  • utilizar interrupciones;
  • controlar procesos;
  • funcionar de forma autónoma;
  • gestionar condiciones de fallo;
  • realizar funciones de diagnóstico.

Las exigencias temporales varían considerablemente entre aplicaciones.

Una computadora para bicicleta puede funcionar con un microcontrolador sencillo porque sus requisitos de procesamiento y tiempo son relativamente modestos.

Una unidad de control de motor necesita capacidades mucho mayores porque los cálculos relacionados con el control del motor deben completarse dentro de tiempos definidos y, además, debe gestionar numerosos sensores, actuadores y comunicaciones.

La idea central puede resumirse de esta manera:

En un sistema embebido de tiempo real, una respuesta correcta no depende solamente de que el resultado sea correcto; también depende de que esté disponible dentro del intervalo de tiempo establecido.

Esta idea conecta directamente la arquitectura del microcontrolador estudiada en el artículo 03 con el diseño de sistemas embebidos.

Los temporizadores proporcionan referencias temporales, las interrupciones permiten atender eventos, los periféricos permiten interactuar con el entorno y la CPU ejecuta el software que coordina estas funciones.

El siguiente paso natural consiste en estudiar cómo estos mecanismos se implementan concretamente en un microcontrolador: registros, temporizadores, interrupciones, prioridades, periféricos y software de aplicación.
